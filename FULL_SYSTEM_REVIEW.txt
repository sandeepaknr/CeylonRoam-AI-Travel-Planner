PROJECT OVERVIEW
----------------
CeylonRoam is a full-stack MERN + Python AI travel platform for Sri Lanka.
It combines deterministic itinerary planning, CLIP-based image recognition,
a Gemini AI chatbot, PayPal payments, and PWA offline support.

Architecture: 3-tier (React Frontend | Node.js API | Python AI Microservice)
Database    : MongoDB (Mongoose ODM)
Ports       : Node.js → 5000 | Python Flask → 5001

SECTION 5: TECHNICAL PIPELINES
================================================================================

--- PIPELINE A: THE SMART ITINERARY PIPELINE ---
    (Deterministic + Generative / Hybrid AI)

STEP 1 — USER INPUT (TripPlanner.jsx)
  Fields: Start Location, Start Date, Number of Days, Budget (LKR),
          Group Size, Transport Mode (Car/Tuk/Bike/Bus),
          Interests (keywords), Vulnerable Members flag

STEP 2 — NODE.JS BRIDGE (tripplanaiController.js)
  - Serialises form data to JSON string
  - Spawns: python itinerary_api.py "<escaped_json>"
  - Streams stdout, parses JSON result

STEP 3 — DETERMINISTIC PROCESSING (itinerary_api.py)
  a. Interest Expansion: enhance_search_keywords() expands user keywords
     e.g. "beach" → ["beach","ocean","coast","surf","coral","galle","mirissa"]
  b. MongoDB Query: Reads places + hotels collections via pymongo
  c. District Routing: Greedy nearest-neighbour algorithm
     - Identifies preferred districts from keyword matches
     - For each day: picks priority district → else nearest unvisited
  d. Transport Costing: cost_per_km + speed_kmph by transport type
  e. Per-Day Loop:
     - get_weather_forecast() → Open-Meteo API → is_raining flag
     - Holiday check from CSV → Poya day warning
     - Hotel selection: within 20km of anchor, fits 70% of daily budget
     - Place selection: ≤35km from hotel, ≤3 places/day, ≤9hr time budget
     - check_accessibility() → warns for mountains/peaks if vulnerable
     - Google Maps URL built from waypoints (urllib.parse.quote)
  f. Budget guard: returns budget_insufficient status if hotel+transport > budget

STEP 4 — LOCAL CONSTRAINT CHECK (itinerary_api.py)
  - Haversine distance calculation (calculate_distance)
  - estimate_visit_time() by category (safari=3.5h, mountain=3h, beach=2h...)
  - force_free_places flag: skips all paid attractions if budget is zero
  - used_places set: prevents duplicate visits across days

STEP 5 — LLM NARRATION (get_ai_story)
  - Structured itinerary dict passed to Gemini prompt
  - Model cascade: gemini-2.5-pro → gemini-2.5-flash → gemini-2.0-flash
  - Returns travel blog-style narrative with title + daily breakdown
  - Node.js attaches ai_story to final JSON → React renders in TripPlanner.jsx

--- PIPELINE B: IMAGE RECOGNITION PIPELINE ---

INPUT:
  User uploads photo in TripPlanner.jsx → sent via FormData to POST /predict

PROCESSING (server.py):
  - PIL opens image → converts to RGB
  - CLIPProcessor encodes image as pixel_values tensor
  - Pre-encoded text prompts: "A photo of {class_name}" × 55 classes
  - model() forward pass (no_grad) → logits_per_image softmax

MODEL:
  - Base: openai/clip-vit-base-patch32 (ViT-B/32 CLIP)
  - Fine-tuned: srilanka_travel_clip_fixed.pth (trained on 55 Sri Lankan places)
  - Device: CUDA if available, else CPU

RESULT:
  - Confidence < 75% → error: "cannot detect clear travel destination"
  - Confidence ≥ 75% → returns predicted_place, district, category,
                        description, confidence %
  - Frontend displays place info + suggests related packages

--- PIPELINE C: GEMINI CHATBOT PIPELINE ---

  User message → POST /chat (server.py)
  → Personalised system prompt (SYSTEM_PROMPT_TEMPLATE with addressee)
  → full_prompt = system_prompt + user_name + "User: {msg}\nRoamy:"
  → Model cascade: gemini-2.5-flash → gemini-2.0-flash → gemini-2.0-flash-lite
  → Returns reply_text → rendered in chat UI

ROAMY PERSONA RULES:
  - Sri Lankan travel expert only
  - Warm, professional tone; occasional "Ayubowan"
  - No slang (no "Machang", "Bro" etc.)
  - Concise: 2-4 sentences or short bullet list
  - Monsoon accuracy: SW = May-Sep, NE = Oct-Jan

--- PIPELINE D: THE OFFLINE-FIRST PIPELINE (PWA) ---

SERVICE WORKER (service-worker.js — Workbox):
  - Powered by: workbox-core, workbox-routing, workbox-strategies,
                workbox-precaching, workbox-cacheable-response

CACHING STRATEGY:
  Layer 1 — Precache (Install phase):
    precacheAndRoute(__WB_MANIFEST) — all build assets (JS, CSS, HTML)
  Layer 2 — App Shell:
    Navigation requests → serve index.html (SPA shell routing)
  Layer 3 — API Data Cache (NetworkFirst):
    - Matches: port 5000 requests OR paths with /api/, /ai/, /packages/
    - cacheName: 'api-data-cache'
    - Allows status 0 (opaque/cross-origin) + 200
    - Falls back to cached data when offline

SYNC QUEUE:
  - POST/PUT/DELETE requests → NetworkOnly (no caching, must have connection)
  - Service worker listens for {type: 'SKIP_WAITING'} message for updates

CURRENCY OFFLINE STORAGE (CurrencyContext.js):
  Pipeline: Live API → localStorage Cache → Static Hardcoded Fallback
  1. Check localStorage (cr_rates_v2) → if < 24h old, use cached rates
  2. Always attempt live fetch from open.er-api.com/v6/latest/LKR
  3. On success: update state + refresh localStorage cache
  4. On failure: use cached OR fall back to STATIC_RATES (hardcoded ~2025)
  rateSource flag: "live" | "cached" | "static" exposed to UI

SECTION 12: BOOKING & PAYMENT FLOW
================================================================================

BOOKING LIFECYCLE:
  Pending → Confirmed → Completed | Cancelled

FLOW:
  1. User browses package → ViewPackage.jsx
  2. Selects date range → POST /api/bookings (creates Pending booking)
  3. Redirected to /payment/:bookingId → PaymentPage.jsx
  4. PayPal button → POST /api/payments/create-order (creates PP order)
  5. User approves in PayPal → POST /api/payments/capture-order
  6. On COMPLETED: Payment record saved + Booking status → Confirmed
  7. adminCommission + providerEarnings calculated at booking creation

SECTION 13: KNOWN ISSUES & RECOMMENDATIONS
================================================================================

ISSUES:
  1. Python path in tripplanaiController.js is absolute (hardcoded to C:\Users\ASUS\...)
     → Must be updated per deployment machine
  2. srilanka_travel_clip_fixed.pth path in server.py is also hardcoded
     → Should use os.path.join(__file__) relative path
  3. SSL verification disabled globally in server.py (dev workaround)
     → Should be removed or scoped for production
  4. PayPal client-id is exposed in App.js source code
     → Should be loaded from environment variable
  5. CORS set to "*" on both servers
     → Should be restricted to known domains in production
  6. tripplanaiController.js uses child_process exec (blocking risk)
     → Consider spawn with streaming or a persistent Flask endpoint

RECOMMENDATIONS:
  1. Move itinerary_api.py to a persistent Flask route (POST /generate)
     instead of spawning a new Python process per request
  2. Add JWT middleware to protect all mutation routes (POST/PUT/DELETE)
  3. Add average rating field to Package model (auto-computed on review save)
  4. Add verified booking tag to reviews (check if userId has a booking)
  5. Implement Redis for session/OTP caching instead of in-memory
  6. Add image compression pipeline (sharp npm) before multer storage
  7. Add admin review moderation panel to delete inappropriate reviews
